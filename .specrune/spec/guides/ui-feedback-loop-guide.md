# UI 盲调防护指南（ui-feedback-loop）

来源：2026-10-22 wordmark 位置连调三轮无效 + 图标素材连错三次的复盘。
两案同根：**无图像输入能力却跳过了内容验证，把用户当唯一验证器**。
2026-10-24 增补：Duo 横屏内容列宽度连调五轮无效（见文末"约束穷举"）。

## 触发场景

- 用户口头描述某个 UI 元素（"左上角的 logo"），要求调整位置/大小/样式
- 需要采用一个图像/图标资产，但无法直接看到它的内容

## 铁律

1. **改 UI 前先截图定位目标**。用模拟器截图 + OCR 拿到目标元素的坐标，确认
   它在哪个视图（哪个文件）里，再动手。OCR 脚本输出 `文本|归一化x|归一化y`，
   足以判断"左上角 logo"到底是登录页品牌区还是侧栏头部。

   ```bash
   xcrun simctl io <udid> screenshot --display=<N> /tmp/shot.png
   swift <ocr-pos脚本> /tmp/shot.png   # 输出 文本|x|y
   ```

   多屏模拟器（折叠屏）注意：GUI 模式下 display 编号会变，逐个截，找有内容的。

2. **UI 修改无效果时，第一动作是核实对象**，不是调参。连续调参两轮仍无反馈
   = 大概率改错了文件。立即截图对比修改前后坐标，确认改动落在用户看的视图上。

3. **不能读图时禁止凭文件名/来源推断图像内容**。验证手段：
   - 与已知参照图做像素 diff（平均差 ≈ 0 即同一张图）
   - 降采样 ASCII 渲染看形状轮廓（16×16 足以分辨 logo 大形）
   - 采样关键位置像素确认配色

4. **SwiftUI 布局机制先想清楚再改**：`layoutPriority` 不改变两个 Spacer 平分
   剩余空间的行为；要让一侧占更多空间用 `Spacer(minLength:)` 或比例布局。
   `contentMargins` 与 safe area 叠加后行为非线性——实测 0→16→36 margins
   造成的实际偏移分别是 0/16/74pt，无法用"加多少平移多少"预测。

5. **宽度/边距类问题先穷举约束点，再动手改任何数值**。"内容没铺满"这类
   症状往往由**多层独立限宽同时生效**造成（本项目一次就叠了三层：内容列
   `maxWidth: 760` 修饰符、ScrollView 系统阅读边距、composer 780pt 上限，
   分居三个文件）。逐条排查工具：

   ```bash
   # 全目录搜所有数值限宽（别加 head 截断、别过度过滤）
   grep -rn "maxWidth: [0-9]\|contentMargins\|maximumContentWidth" --include='*.swift' ios/
   ```

   一个数值修完症状仍在 = 还有别的约束在起作用，**回到穷举**，不是继续
   调刚改的那个值。

6. **用户"反差观察"是条件性约束的直接证据**："A 场景正常、B 场景异常"
   （如"边栏打开时正常、隐藏时变窄"）= 某个限宽只在列宽超过阈值时生效。
   拿到数字算差：detail 列 951pt 异常、651pt 正常 → 约束阈值在两者之间，
   直接 grep 这个区间的常量（760 命中）。这比盲改五轮快一个数量级。

8. **症状报告必须先拿到用户指认的样本，再下结论**（2026-10-24 换行
   调查两次翻车复盘）。"有些段落提前换行"这类报告，第一步是让用户
   指认：哪一段（原文开头）+ 断在哪。**用自己猜/编的样本做验证，
   验证的是自造样本，不是用户的症状**——本轮用自造样本两次得出
   "无 bug"结论两次被用户反驳，拿到指认样本后一轮钉死（真 bug 或
   平台行为）。铁律：没有指认样本前，禁止对症状类报告下任何结论。

9. **临时诊断日志统一带 `AA-DIAG:` 前缀注释**。本轮加的布局日志
   清理时两次删坏括号导致编译失败。约定：临时诊断代码每处首行
   `// AA-DIAG: <原因>`，清理时 `grep -rn "AA-DIAG" ios/` 逐处删，
   删后必须构建验证再继续。

7. **纯视觉修正优先用可预测手段**。`.offset` 是纯平移不触发重新布局但会
   裁掉溢出侧；`.padding` 会触发 SwiftUI 布局协商且和 margins/safe area
   叠加后偏移量不可预测。改完必须量化复核（截图测边界），不能只看构建
   通过。

## 已踩坑记录

- 商店版 "SpecRune Harness.app" 图标是 DeepSeek 鲸鱼（DSH 换壳），仓库
  `apps/desktop/resources/icon.png` 也是鲸鱼；`icon-macos.png` 才是 SpecRune
  专属。用户提供的 `.VolumeIcon.icns`（黑底符文 + 蓝节点）是最终正解。
- 模拟器相册默认为空，塞照片用 `xcrun simctl addmedia <udid> <图片>`。
- 屏幕左右边缘 1-2pt 的渲染伪影细线会被像素检测误判为"内容贴边"，
  量化边界时排除边缘 8-10pt 再取值，否则所有测量被污染。
- 模拟器 Debug-iphonesimulator 与 Debug-iphoneos 是两个产物目录；只为
  真机构建的改动不会出现在模拟器上，反之亦然。换环境复现前先确认装的
  是不是新构建（本次模拟器量化"780 限宽仍在"就是装了旧模拟器构建）。

## 2026-10-25 增补：Duo 双屏键盘适配连败 ~10 轮（第三次重犯）

新维度：不是"改错文件"，而是**在语义未知的 API 上做参数微调**+**测量链被
测对象污染**+**视图实例身份被忽略**。同日 10-24 复盘的"约束穷举"没覆盖这些。

10. **新平台 API 先做语义探针，再做业务**。首次使用 iOS 27.1 arrangement
    这类新 API 时，外部文章的符号名/API 形状不可信（本次 "SwiftUI
    ArrangementView" 系 AI 辅助写作失实，SDK swiftinterface 0 匹配）。
    动手前先 grep SDK 头文件/swiftinterface 实证符号与签名：
    `xcrun --sdk iphonesimulator --show-sdk-path` +
    `grep -r <符号> .../Frameworks/*/Headers`。

11. **参数微调连续两轮无效 = 停止调参，改结构**。本次 51pt 偏移修正、
    padding 抬升量、0.5/1.0 系数全是参数微调，全部无效或引入新 bug；
    换成 keyboardLayoutGuide 系统锚定（结构变更）后一轮解决。判断依据：
    修正量与观测位移不一致（改 51pt 位置没动）= 参数根本不控制该行为，
    所在层次错了。

12. **测量探针必须与被测布局解耦**。挂在被测视图内部、且其尺寸参与
    布局的探针会形成反馈循环（本次 lift 值振荡 395↔495、kb 值逐轮漂移）。
    规则：探针用窗口坐标绝对量 + 固定位置（1x1）+ 不参与任何布局提案；
    拿到读数后先做稳定性验证（同一状态触发两次读数应一致）再用于布局。

13. **有焦点的视图禁止在条件分支间迁移**。SwiftUI 分支切换 = 实例重建
    （本次 pane↔浮层切换导致输入框丢焦点、键盘秒收回的死循环）。
    交互中（聚焦中）的视图必须在稳定容器里，用位置/约束变化替代
    容器切换。

14. **模拟器验证的边界要预先声明**。Duo 模拟器：Device Hub 状态按钮与
    铰链事件流不同步（显示 Expanded 实报 partiallyOpen 127.8°）、软键盘
    无法可靠拉起、headless 重启后帧缓冲不渲染需 GUI 解锁。凡模拟器验证
    失败或矛盾，先怀疑环境再怀疑代码；真机行为与模拟器冲突时，真机为准。
    **2026-10-27 增补（Xcode 27/Device Hub 实测）**：`simctl io` 已无
    `sendTap`（仅截图/录屏）；`recordVideo` 被 kill 后 host 端录制锁
    死（"Host recording is already in progress"）且 SIGTERM 不收尾产
    0 字节文件；并行连拍有撕裂伪影（半渲染帧混入，OCR 位置不可信），
    串行拍 0.5s/张又抓不到 <0.5s 瞬态。可用：Device Hub 把模拟器内容
    的 accessibility 树透传到 Mac（orca computer-use 可读按钮/文本，
    点击坐标映射失真常落错元素，只读不点）；无图像输入能力时 OCR
    （swift Vision 脚本）+ ASCII 降采样渲染可判读结构轮廓。瞬态视觉
    bug 的最快观测器仍是真机用户。

15. **自绘手势/跟手动画之前，先找系统已有的交互**。2026-10-25 指令面板
    跟手拖动抖动连败 5 轮（transformEffect/offset/材质遮罩/手势竞争全试）
    后用户自己发现：timeline 已有的 `scrollDismissesKeyboard(.interactively)`
    早就实现了"下拽消息流 → 键盘+输入框+面板跟手下去"，系统动画零抖动。
    规则：要做一个手势效果前，先 grep 本仓库和想系统控件
    （ScrollView dismiss、sheet 拖拽、keyboardLayoutGuide），系统有的
    永远比自绘稳。
    **2026-10-26 收官补记**：自绘跟手并非不可行——五连败的真正根因是
    `DragGesture` 默认 `.local` 坐标系随被拖视图自身移动，translation
    被自己污染形成震荡回路。`coordinateSpace: .global` 一行即根治
    （指令面板标题行拖拽收键盘已上线，真机顺滑）。铁律 15 仍成立
    （优先系统），但当系统没有等价交互时，全局坐标 + transformEffect +
    松手事务分离（commit 瞬时归零交布局动画 / 取消 spring 回位）是
    自绘跟手的可靠配方。

16. **动态出现的 UI 别放布局流，先想浮层**。2026-10-26 指令面板占位
    （VStack 流内）引发连锁：弹出推动消息流视口、高度参与键盘跟随
    对齐计算导致"末条消息不贴输入框"（两轮误修对齐逻辑，真因在结构）。
    弹出/收起类 UI 用 overlay + 明确锚点偏移；布局流内的高度变化会
    重分配视口、触发滚动跟随、改变对齐参照，一处占位三处涟漪。

17. **诊断代码不得内联调用有副作用的方法**。2026-10-26 键盘跟随调试：
    日志里 `String(describing: scrolling.begin(request))" 内联调用了
    begin——它消费 pendingBottomRequest，guard 里的第二次调用拿 nil，
    诊断代码自己制造了 bug，误导一轮排查。诊断只读快照（打印已捕获
    的值），或先 `let r = f(); log(r)` 再用 r。
